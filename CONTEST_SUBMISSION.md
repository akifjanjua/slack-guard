# RailCall Contest Entry — Slack Guard

## Title

Slack Guard — Governed Slack Integration

## Repository

https://github.com/akifjanjua/slack-guard (branch `master`) — repository visibility and public link to be confirmed once the remote is created.

## Description

Slack Guard is a governance-first RailCall module for Slack workspaces, built against a 39-command, 3-tier plan (reads, low-risk writes, human-airlocked high-risk writes). v0.4.1 ships all 39 commands against the real Slack Web API. Three governance presets, set via an optional field on the same Integrations card as the bot token, give a real functional restriction — not just a documented label: Open Community Hardened hard-blocks the four highest-abuse Tier 3 commands outright, in the handler itself, before any network call, regardless of approval.

Slack Guard resolves credentials only through RailCall's vault helper, uses certifi-backed verified HTTPS, never invokes curl or another subprocess, and actively redacts credentials from errors. `module.json` declares a `requires` sandbox block (`network: ["slack.com"]`, `subprocess: false`, `filesystem_writes: []`) that RailCall Station enforces at handler-load time. Unlike Notion Guard's/Linear Guard's REST APIs, Slack's Web API always returns HTTP 200 and signals failure through `{"ok": false, "error": "<code>"}`; the handler treats that as a definitive rejection distinct from a true transport-level failure.

This entry is being filed while the module is still in active build-out — see `CHANGELOG.md` for exactly what is live. Full end-to-end verification evidence (signature, real Slack call, signed receipt) will be added here as each build-order step completes.

## Known platform issues found during this evidence pass (RailCall Station, not Slack Guard)

1. **`external_api_touched` mislabeled on every failed write.** `routes/commands.py`'s `execute_command` computes `external_touched` correctly on the success path (`ext = cmd.get("provider") != "railcall" ...`) but the `except Exception` branch that builds a `failed_safely` receipt never passes `external_touched` at all, so it silently defaults to `False` regardless of whether the handler's exception happened before or after a real network round-trip. Reproduced live: the second `kick_user_from_channel` receipt above has `note: "...Slack rejected the request: user_not_found"` — a Slack-defined error code that cannot exist without Slack Guard's `_request` actually reaching `slack.com` and getting a real response back — yet the receipt still says `external_api_touched: false`, identical to the *previous* receipt where the call was blocked before any network attempt.
2. **Long JSON-string output fields get corrupted, not just trimmed, in the sealed receipt.** `approval_airlock.py`'s `redact()`/`_redact_output()` truncate any string value over 300 characters to `value[:300] + "…"` before sealing `output` into the receipt — applied uniformly to every module. A field like Slack Guard's `channels_json` is itself a JSON-encoded array; truncating it mid-string leaves invalid JSON in the receipt's human/programmatic-readable `output` (the retry hash `post_execution_result_hash` still binds the real untruncated value per the code's own comments, so nothing is lost cryptographically — only the display/consumption copy breaks). Reproduced live: `slack.list_channels`' receipt (`cmd_20260905T184904Z_slack_list_channels_a1c95aa8_executed_0018.json`) has a 301-character `channels_json` that fails `json.loads()`.

Both reported to the module owner; not filed on the forum by this session.

## Trust declaration

Slack Guard's signed manifest declares `allowed_destinations` as exactly the Slack API host (`slack.com`) and zero LLM/model-provider entries. The module talks only to the Slack Web API and does not send workspace data to a model-provider SDK or RailCall model-completion primitive.
